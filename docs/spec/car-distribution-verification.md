# CAR配布・取得時の破損検出と電子署名

Status: adopted behavior contract for planned Phase 82; not implemented.
Decision date: 2026-10-09.
Implementation ledger: [Phase 82](../phase/phase-82.md).
Consumer ledger: [CNCF Phase 104](../../../cloud-native-component-framework/docs/phase/phase-104.md).

## 適用範囲

本仕様は、コンポーネント・リポジトリで公開するCARと、そのCARを
ダウンロードしてローカルキャッシュへ登録する処理を対象とする。
SHAは破損を防ぐ処理そのものではなく、破損した取得物を検出して受け入れないために使う。
電子署名は署名後の変更を検出し、信頼する鍵の所有者による署名を確認する。

通常の開発用CAR生成には、内部ファイルのSHA一覧作成や署名を要求しない。
本仕様は将来の公開・取得契約であり、現在のPhase 71.5の実装、台帳、拒否記録、
レビュー履歴や既存リポジトリ形式をこの文書の作成だけで変更しない。

## 配布物

- 完成したCAR全体のバイト列からSHA-256を計算し、隣接する
  `<archive>.car.sha256`として公開する。この取得契約ではSHA sidecarを必須とする。
- 電子署名は任意。署名する場合は、完成したCAR全体を対象に外部署名を公開する。
- CAR、SHA、任意の署名は同一のリリースに対応する。署名後の再圧縮も別のバイト列であり、
  SHAと署名を再生成する必要がある。
- リポジトリの署名有無の表現と署名取得方法を定義する。
  明示的な未署名と、署名を取得できない通信障害・不完全な公開を区別する。
- 署名方式、署名ファイルの拡張子、SHA sidecarの構文、鍵情報のwire形式は
  P82-01で確定する。OpenPGPの`.asc`は候補であり、本仕様による採用決定ではない。

## ダウンロードとキャッシュ登録

取得処理は次の順序で動作する。

1. CARを、ローディング対象にならない一時取得領域へダウンロードする。
2. ダウンロードが完了したCAR全体のSHA-256を計算し、外部SHAと照合する。
3. 署名がある場合は、信頼する提供者の公開鍵で、その同じCAR全体の署名を検証する。
4. 成功したそのCARを、正式なローカルキャッシュへ登録する。
5. キャッシュ登録後に、展開と通常のコンポーネントローディングを行う。

SHAの欠落・不正・不一致、取得失敗、不正な署名、許可されていない署名鍵、
必要な鍵情報を検証できない場合は、取得失敗とし、そのCARを正式キャッシュへ登録しない。
署名の取得・検証失敗を未署名扱いへ切り替えてはならない。
検証後の再ダウンロード物や別ファイルを、検証済みの物として登録してはならない。

既存の利用可能なキャッシュは、失敗した更新物と区別する。
一時取得物、失敗物、登録途中の物を、成功したキャッシュとして返してはならない。
成功の公開方法、キャッシュ所有者と書き込み権限はP82-03で実装・検証する。

## 署名の有無

| CARの状態 | 取得時の扱い |
| --- | --- |
| 未署名、SHA一致 | 受け入れる。電子署名による改竄検証は行わない。 |
| 署名あり、SHA一致、許可された鍵で署名検証成功 | 受け入れる。 |
| SHAが欠落、不正または不一致 | 拒否する。 |
| 署名あり、署名が不正・未対応または鍵が許可されていない | 拒否する。 |
| 署名ありと判明しているが署名を取得できない | 拒否する。 |
| 署名有無を取得障害のため判断できない | 取得失敗とする。 |

公開配布でも電子署名は必須にしない。外部SHAだけでは提供者の真正性は保証しない。
署名任意の契約は、署名の存在自体を偽装して未署名に見せる攻撃への一般的な保証をしない。
必須署名ポリシーや署名除去対策は、この合意の条件に追加しない。

## 公開鍵の配布と信頼

コンポーネント・リポジトリは、namespaceごとに署名を許可する提供者の公開鍵と、
有効期間・更新・失効情報を配布する。公開鍵の配布と、その鍵を信頼する判断は区別する。

CNCFのリポジトリ設定に、利用者が信頼すると決めたリポジトリの起点となる公開鍵を登録する。
提供者の鍵一覧は、その信頼の起点から検証できる署名付き情報として取得する。
ダウンロードしたCARや鍵一覧に同梱された鍵を、それだけで新しい信頼の起点にしてはならない。

署名検証では、CARのnamespaceに許可された有効な鍵であることも確認する。
鍵一覧を署名検証できない場合や、必要な情報が期限切れの場合に、無検証の鍵へ切り替えない。
リポジトリの信頼鍵と提供者の鍵の更新・失効手順を定義する。
既存キャッシュに対する鍵失効の反映、失効情報の更新頻度、旧情報の再提示への対策は
P82-01で明示する。TUFの採用範囲を同じ作業で評価する。

秘密鍵は公開リポジトリ、CAR、取得キャッシュに格納しない。
署名する公開処理と、公開鍵だけを使う取得処理を分離する。

## キャッシュ再利用とローディング

検証済みのCARを登録後に変更しないキャッシュ運用を前提に、通常のキャッシュヒットや
CARローディングごとの全体SHA・電子署名の再検証は行わない。
これはCARの変更不能性をハッシュ台帳で毎回証明する方式ではない。
キャッシュの書き込みを取得処理に限定し、編集可能な開発出力と分けて管理する。

更新・差し替え・再取得は新しい取得として検証する。キャッシュの手動編集は通常運用に含めない。
変更可能な保存方式を採用する場合は再利用時の保証を再設計する必要があり、
一度検証したという事実だけで変更後のバイト列を信用してはならない。
展開後のファイルの継続的な改竄監視は本仕様の対象外である。

CAR内のclass、定義、画像などは、受け入れたCAR全体への署名でまとめて対象となる。
個々のclassやリソースの読み込みに、独自のSHA照合を組み込まない。
CAR内部の全ファイルSHA一覧、全ファイル集合照合、digest照合を復活させない。

## 識別情報・runtime・ABIの役割

- コンポーネントの識別情報（namespace・名前・バージョン）の確認を維持する。
  取得先で要求した識別情報とCARの宣言の一致、および既存の宣言間整合性を扱う。
- 現在のCNCFがCARのruntime範囲を満たすかは、使用時に引き続き確認する。
  同じキャッシュを異なるCNCFバージョンで使う場合も、この確認は省略しない。
- `abi-manifest.json`は、利用者が公開サービス、操作、型、依存関係や更新影響を
  調べるためのメタデータとして提供する。
- CARローディングのためだけのABI宣言の存在必須化・簡易形式検証は外す。
  ABIメタデータの生成・公開時の整合性確認と、利用ツール自身の必要な形式検証へ責務を置く。
- `cozy lint abi`による前リリースとの公開契約比較は維持する。
  ローディング時の簡易検査を、バイナリ互換性の保証とは呼ばない。
- パスの安全性、必要な実行ファイル、通常の形式・I/O検証は維持する。

## Executable Specificationの予定

未署名の正常取得、署名付きの正常取得、転送破損、CARとSHAを同時に変更した場合の
署名失敗、自己生成した鍵への差し替え、署名取得障害、鍵情報の改竄・期限切れ、
許可された鍵更新、キャッシュ登録前の失敗、登録後の再利用と更新をGiven/When/Thenで証明する。
バイト列の変更とSHA照合にはProperty-Based Testingを用いる。
識別情報・runtime検証の維持と、ABIメタデータを実際の利用ツールが読む経路も確認する。

実装先の仕様クラスと実際の結果はPhase 82の実装時に関連付ける。
本書に記載したシナリオは未実行であり、現時点でExecutable Specificationの通過を主張しない。
