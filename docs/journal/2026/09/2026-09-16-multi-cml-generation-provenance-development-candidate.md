# Multi-CML Generation Provenance Development Candidate

Date: 2026-09-16
Status: triaged development candidate; no implementation acceptance

## DEV-031: Multi-CML generation provenance and sbt-cozy bridge

### Discovery

`simplemodeling-model` is a valid CML producer with both
`src/main/cozy/address.cml` and `src/main/cozy/user-profile-values.cml`.
Its focused EntityId producer verification reaches delegated generation, where
both inputs emit valid per-run `cozy.generation-provenance.v1` evidence.

The current sbt-cozy installation then rejects the two evidence documents.
The current v1 contract intentionally carries one CML source identity and
forbids selecting one of several manifests arbitrarily. This candidate does
not treat either CML source as invalid and does not weaken that fail-closed
rule by suppressing provenance.

### User direction

Cozy must support multiple CML inputs. Cozy is the design and contract owner;
sbt-cozy follows that accepted contract as the integration and installation
layer. The affected producer is a downstream acceptance driver, not the owner
of a local configuration workaround.

### Required outcome

Define and implement one explicit multi-CML provenance contract that preserves
every participating project-relative CML source identity and its accepted
generated-output evidence. The contract must make a one-CML project remain
valid, and must reject missing, conflicting, stale, or ambiguously rebound
evidence rather than silently choosing a source.

The design must account for generated paths shared by several CML inputs:
identical bytes may be represented once in the project-level result, while
different bytes claimed for the same generated path must fail. It must not
introduce a new hash-derived identity or a generic internal hash-control
mechanism; declared source identities, project-relative paths, and the normal
generator/output contract remain the ownership boundary.

### Ordered ownership

1. **Cozy** owns the multi-source provenance representation, validation,
   project-level rebind behavior, backward-compatibility decision for existing
   v1 evidence, and focused executable specifications.
2. **sbt-cozy** owns collection of all isolated delegated manifests, exact
   handoff to Cozy's accepted aggregate/rebind operation, installation of the
   project-level side output, incremental availability checks, and plugin
   integration specifications.
3. **simplemodeling-model** remains the first real multi-CML driver: after the
   upstream contract and bridge are accepted, rerun the blocked `EntityIdSpec`
   focused verification and continue its independent Phase 74.1 acceptance.

### Acceptance drivers

- Cozy accepts two valid delegated manifests from distinct CML sources and
  produces one deterministic project-level provenance result covering both.
- Cozy rejects source omission, duplicated/ambiguous source identity, stale
  evidence, and contradictory generated bytes for one output path.
- sbt-cozy successfully generates a two-CML CAR project through the accepted
  Cozy contract, retains incremental side-output availability, and preserves
  one-CML project behavior.
- The real `simplemodeling-model` two-CML driver can run its focused producer
  test without a source-selection workaround or provenance bypass.

### Non-goals

- Do not change either `simplemodeling-model` CML source merely to make it
  single-source.
- Do not suppress generation provenance, select a manifest by order, or make
  an unrelated EntityId/JobDefinition policy decision.
- Do not implement CNCF Phase 74.2 or any runtime consumer work here.
