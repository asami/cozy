## Dashboard Role

The Glossary Dashboard should explain and monitor how glossary terms become
connected knowledge.

The RDF and Project cards should sit after the Glossary Workflow and Summary
cards conceptually:

```text
Glossary Summary
  -> current state

Glossary Workflow
  -> how terms are extracted and refined

RDF card
  -> how terms are connected to graph knowledge

Project card
  -> how terms are connected to CML/project knowledge
```

These cards should not duplicate the Missing Analysis card. They may show
compact health counts, but concrete missing-term lists remain owned by Missing
Analysis.

## RDF Card

### Card Name

Japanese UI:

- `RDF接続`

English UI:

- `RDF Connections`

### Purpose

The RDF card shows how glossary terms participate in graph-facing knowledge.

It answers:

```text
How well are glossary terms connected to RDF knowledge?
```

The card should help readers understand that glossary terms are not only index
entries. They are RDF-facing knowledge anchors that can connect to:

- BoK RDF triples
- external resource URIs
- RDF node detail / 1.5+hop Information View
- same-resource / same-concept alignment
- provenance and evidence triples

### Primary Metrics

Recommended top metrics:

| Metric | Meaning |
| --- | --- |
| RDF-linked terms | number of terms with at least one `rdf_refs` entry |
| RDF triples | total RDF triples in the BoK graph metadata |
| RDF nodes linked to terms | number of graph nodes associated with glossary terms |
| External URI links | count of RDF refs that point outside the BoK site |

If a value cannot be derived yet, the card should omit it or show `-`; it
should not invent a number.

### Connection Breakdown

The card should show a compact breakdown of RDF link types when metadata is
available:

- outgoing RDF refs
- incoming RDF refs
- identity links
- descriptive links
- hierarchy links
- provenance links

These categories should align with the 1.5+hop Information View vocabulary:

- `information.identity`
- `information.description`
- `information.links`
- `information.hierarchy`
- `information.provenance`

### Suggested Layout

```text
RDF接続

用語をRDFグラフ上の知識ノードとして確認します。

[RDF接続済み用語] 18 / 24
[RDFトリプル] 109
[用語連携ノード] 32
[外部URI] 12

接続内訳:
identity / description / links / hierarchy / provenance

主な確認:
- 用語がRDFノードに接続されているか
- 説明に必要な1.5+hop情報が見えるか
- 外部知識との同一性・近接性が分かるか
```

### Suggested Japanese Text

Lead:

```text
用語をRDFグラフ上の知識ノードとして確認し、説明・同一性・階層・根拠の接続状態を見ます。
```

Checkpoints:

```text
RDFノード接続 / 1.5+hop情報 / 外部URI / 根拠
```

### Suggested English Text

Lead:

```text
Inspect glossary terms as RDF graph knowledge nodes and review description, identity, hierarchy, and provenance links.
```

Checkpoints:

```text
RDF node links / 1.5+hop Information / external URIs / provenance
```

### Link Behavior

Useful links:

- RDF dashboard or RDF graph page
- filtered RDF view for glossary terms
- term-linked RDF node list, if generated

The card should not include Japanese/English glossary index links. Those belong
to the language-index card.

### Data Sources

Expected inputs:

- `metadata/glossary/terms.json`
- RDF graph metadata generated by Cozy/SmartDox
- term `rdf_refs`
- RDF node metadata that records related term ids
- Information View metadata when available

The first implementation can use only `terms.json` and existing RDF graph
counts if the full Information View metadata is not available.

### Non-Goals

- Do not render the full RDF graph inside this card.
- Do not list every RDF-linked term.
- Do not replace the RDF graph page.
- Do not expose raw predicate lists as the primary card content.
- Do not make the card depend on external network access.

### Acceptance Criteria

- The Glossary Dashboard has an RDF card titled `RDF接続` in Japanese
  operation.
- The card shows at least RDF-linked term count and total RDF triple count when
  metadata is available.
- The card explains that RDF is the graph-facing knowledge representation for
  glossary terms.
- The card links to the RDF graph/dashboard surface.
- Missing RDF links remain handled by the Missing Analysis card.

## Project Card

### Card Name

Japanese UI:

- `プロジェクト接続`

English UI:

- `Project Connections`

### Purpose

The Project card shows how glossary terms connect to project-side knowledge,
especially CML metadata and publication/project metadata.

It answers:

```text
How well are glossary terms connected to executable or modeled project knowledge?
```

The card should help readers understand that CML/project linkage is distinct
from RDF linkage:

- RDF linkage explains graph knowledge.
- Project linkage explains model, implementation, and publication knowledge.

### Primary Metrics

Recommended top metrics:

| Metric | Meaning |
| --- | --- |
| CML-linked terms | number of terms with at least one `cml` link |
| Project-linked terms | number of terms connected to project metadata |
| Projects | number of known BoK project entries |
| Source-only projects | number of project references using development-directory/path mode |

If a BoK is in early development and a project is source-only/path-based, the
card should mark that as intentional development operation, not as an error.

### CML Connection Breakdown

The card should show a compact CML linkage breakdown when metadata is
available:

- entity
- value / powertype
- event
- operation
- statemachine
- rule
- component / service

For CML entity links, the card may show a small `entityKind` summary if the
metadata is available:

- master/resource
- document
- workflow
- task
- actor
- asset
- system

This should remain secondary. The card should not become an `EntityKind`
reference table.

### Suggested Layout

```text
プロジェクト接続

用語をCMLモデル、プロジェクト、Publication metadataに接続して確認します。

[CML接続済み用語] 8 / 24
[プロジェクト接続用語] 6
[プロジェクト] 1
[開発ディレクトリ直読み] 1

CML接続:
entity / value / event / operation / statemachine / rule

主な確認:
- 用語がCML要素に接続されているか
- 永続オブジェクトはentityKindで用途が分かるか
- 開発中projectはsource-onlyとして扱われているか
```

### Suggested Japanese Text

Lead:

```text
用語をCMLモデル、プロジェクト、Publication metadataへ接続し、知識が実装・モデル側でどう表現されるかを確認します。
```

Source-only note:

```text
開発ディレクトリ直読みのprojectはsource-only運用として扱い、artifact未配布を異常状態として表示しません。
```

CML note:

```text
CMLのentityは永続オブジェクトであり、用途はentityKindで分類します。
```

### Suggested English Text

Lead:

```text
Connect glossary terms to CML models, projects, and publication metadata to inspect how knowledge is represented by implementation-side models.
```

Source-only note:

```text
Path-based development projects are treated as source-only operation; undistributed artifacts are not shown as errors.
```

CML note:

```text
CML entities are persistent objects, and their purpose is classified by entityKind.
```

### Link Behavior

Useful links:

- project dashboard
- project detail pages
- term-linked CML element list, if generated
- publication metadata detail pages, if generated

The card should not link to commit/upload workflows. Those are BoK operation
workflows, not glossary analysis surfaces.

### Data Sources

Expected inputs:

- `metadata/glossary/terms.json`
- term `cml` links
- project metadata generated by `cozy bok update-publication`
- publication registry metadata
- project reference configuration for `repository: path`, `repository: local`,
  or `repository: public`
- CML metadata extracted from referenced projects

The first implementation can use only term `cml` links and known project
metadata counts.

### Development-Directory Operation

For early BoK projects such as KnowledgeHub, project references may use:

```yaml
projects:
  nict-knowledgehub:
    repository: path
    path: ../nict-knowledgehub
```

In this mode:

- Cozy reads project metadata directly from the development directory.
- Artifacts may be undistributed.
- The dashboard should show this as source-only development operation.
- The dashboard should not label undistributed artifacts as missing/error when
  the project is intentionally path-based.

### Non-Goals

- Do not render full project pages inside this card.
- Do not run project scans from the browser.
- Do not expose raw repository internals as primary card content.
- Do not treat source-only path operation as an error.
- Do not replace project dashboard/detail pages.

### Acceptance Criteria

- The Glossary Dashboard has a Project card titled `プロジェクト接続` in
  Japanese operation.
- The card shows CML-linked term count when metadata is available.
- The card distinguishes project/CML linkage from RDF linkage.
- The card explains CML `entity` / `entityKind` at a high level.
- Path-based project references are shown as source-only development operation,
  not as missing artifacts.
- Detailed project pages remain the primary surface for project metadata.

## Combined Placement

Recommended ordering on the Glossary Dashboard:

1. Glossary Summary
2. Glossary Workflow
3. Type Analysis Routes
4. RDF Connections
5. Project Connections
6. Missing Analysis
7. Language Index
8. Recent Terms

The exact layout may vary by viewport, but RDF and Project cards should appear
near the workflow because they represent the two main connection targets after
term curation.
