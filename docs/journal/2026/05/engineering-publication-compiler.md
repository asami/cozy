# Summary

This note describes the evolving role of Cozy in the AI-era publishing and
engineering knowledge pipeline.

Originally, Cozy focused primarily on DSL/model compilation.

However, in the AI era, software projects themselves become engineering
knowledge sources.

As a result, Cozy evolves toward:

- semantic engineering extraction
- publication model generation
- artifact packaging
- engineering metadata normalization
- AI-facing catalog generation

This note organizes the relationship between:

- source repositories
- publish.d
- website.d
- warehouse

and clarifies the architectural responsibilities of Cozy.

# Background

SimpleModeling.org currently contains:

- multilingual engineering articles
- ontology
- glossary
- schema
- RDF/JSON-LD exports
- SmartDox-based narrative knowledge

At the same time, sample projects and CNCF runtime projects now contain
valuable engineering knowledge:

- topology structure
- deployment structure
- quality attribute implementation
- observability configuration
- operational verification
- runtime capability patterns

In the AI era, these repositories are not merely source code repositories.

They become:

```text
machine-usable engineering knowledge sources
```

Therefore, an extraction and publication pipeline becomes necessary.

# Three-Layer Publication Architecture

The current direction naturally evolves toward three major layers:

```text
source repositories
    ↓
cozy extraction/publication
    ↓
publish.d
    ↓
SmartDox site rendering
    ↓
website.d

release artifacts
    ↓
warehouse
```

# Layer Responsibilities

| Layer | Role |
|---|---|
| source repositories | mutable development source |
| Cozy | semantic extraction/compiler/publication |
| publish.d | generated semantic publication workspace |
| SmartDox site | rendering/presentation/navigation |
| website.d | generated website projection |
| warehouse | persistent artifact storage |

# `website.d`

## Purpose

`website.d` is the generated website projection.

Characteristics:

- fully regeneratable
- disposable
- presentation-oriented
- rendering-focused

Examples:

- HTML
- JSON pages
- catalog pages
- multilingual projections
- generated navigation

`website.d` should be rebuildable at any time.

# `publish.d`

## Purpose

`publish.d` acts as the semantic publication workspace.

This layer is generated by Cozy.

It contains normalized engineering publication data extracted from projects.

Examples:

- sample metadata
- topology metadata
- generated catalog entries
- source projections
- verification metadata
- AI-facing semantic metadata
- generated article fragments

## Characteristics

`publish.d` is:

- generated
- normalized
- semantic
- rebuildable
- curated

Unlike `website.d`,
this layer represents:

```text
canonical publication knowledge
```

rather than final rendering.

# `warehouse`

## Purpose

`warehouse` stores persistent release artifacts.

Examples:

- Maven artifacts
- CAR
- SAR
- ZIP packages
- release bundles
- checksums
- historical releases

## Characteristics

`warehouse` is:

- persistent
- versioned
- append-oriented
- downloadable
- historical

Unlike `publish.d`,
warehouse contents are preserved over time.

# Why Cozy Owns Publication Generation

## Core Reason

The generation of `publish.d` and warehouse artifacts is not merely
site rendering.

It requires:

- semantic repository understanding
- topology extraction
- metadata normalization
- engineering graph generation
- artifact packaging
- release publication

These are compiler-like responsibilities.

Therefore they naturally belong to Cozy.

# Why This Does Not Belong in SmartDox Site

SmartDox site should remain focused on:

- rendering
- presentation
- navigation
- multilingual projection
- catalog visualization

If semantic extraction and artifact packaging are added into the site
generator, responsibilities become mixed.

That would combine:

```text
site rendering
+
semantic extraction
+
artifact publishing
```

inside one layer.

The separation becomes unclear.

# Cozy as Engineering Publication Compiler

The emerging role of Cozy can be summarized as:

```text
engineering semantic compiler
+
publication compiler
+
artifact publisher
```

This is broader than traditional model compilation.

Cozy evolves toward:

```text
source repository
    ↓
semantic engineering model
    ↓
publication knowledge
    ↓
runtime/distribution artifacts
```

# Project-local Cozy Config Update

Implemented project-local defaults through `.cozy/config.yaml`.

The file is treated as a Cozy project config, not as an sbt-cozy-only setting file.
It is used by Cozy CLI operations and by sbt-cozy defaults.

Resolution order:

1. explicit Cozy CLI options
2. explicit `build.sbt` settings when invoked through sbt-cozy
3. `.cozy/config.yaml`
4. built-in defaults and environment fallbacks

Publication metadata now uses:

- `name`: stable slug for URLs, file names, and BoK keys
- `title`: human-readable display title
- `path`: optional SmartDox site publication path

`id` is no longer part of the publication CLI/config surface.

Example:

```yaml
publication:
  name: textus-tutorial
  title: Textus Tutorial
  path: textus/tutorial/textus-tutorial
  kind: sample-multi
  output: target/publish.d
  samples_dir: samples
```

The `sample-multi` detector recognizes repositories that keep independent sbt sample projects under `samples/*/build.sbt`, such as `cncf-samples`. The planned publication for that repository can use `name: textus-tutorial` and `path: textus/tutorial/textus-tutorial`.

# Distribution Operation Split

Release binary distribution is separated from development publication.

Development operations:

- `cozyPublishProject`: generates BoK publication sources such as `publish.d`
- `cozyPublishCAR` / `cozyPublishSAR`: copy archives into the development local repository

Release operations:

- `cozyDistributeCAR`: copies the CAR archive into the release distribution repository
- `cozyDistributeSAR`: copies the SAR archive into the release distribution repository
- `cozyDistribute`: dispatches to CAR or SAR distribution based on `cozyPackaging`

Recommended config:

```yaml
publication:
  name: textus-tutorial
  title: Textus Tutorial
  path: textus/tutorial/textus-tutorial
  output: /Users/asami/src/dev2025/simplemodeling-org/publish.d

distribution:
  repository: /Users/asami/src/maven-repository
  require_release_version: true
```

The distribution tasks reject `SNAPSHOT` versions by default, so binary distribution happens only through explicit release operations.

# Warehouse Indexing

Cozy now treats the warehouse as the source of truth for distributed binary artifacts and generates artifact/release metadata into `publish.d`.

Operation:

```console
cozy index-warehouse <warehouse-dir> --save=<publish.d> --name=<publication-name> [--title=<title>]
```

sbt-cozy integration:

```console
sbt cozyIndexWarehouse
```

Configuration:

```yaml
warehouse:
  repository: /Users/asami/src/maven-repository
  maven:
    coordinates:
      - org.example:textus-tutorial_3
  repository_artifacts:
    include:
      - car
      - sar
    modules:
      - textus-tutorial
```

Rules:

- Maven artifacts are indexed from `warehouse/maven/<group path>/<artifactId>/<version>`.
- CAR artifacts are indexed from `warehouse/repository/car/<module>/<version>/<name>-<version>.car`.
- SAR artifacts are indexed from `warehouse/repository/sar/<module>/<version>/<name>-<version>.sar`.
- Repository artifact indexing is limited to configured modules. If no module is configured, the publication name is used.
- Cozy computes SHA-256 and reads `.sha1` / `.md5` sidecars when present.
- SNAPSHOT versions are included but latest release prefers a non-SNAPSHOT version.
- SmartDox site consumes `publish.d` only; it should not scan the warehouse directly.

Generated metadata:

- `metadata/artifacts/maven/<name>.yaml|json`
- `metadata/artifacts/repository/<name>.yaml|json`
- `metadata/releases/<name>.yaml|json`
