# Core起点・makeレベルの成果物更新

Date: 2026-09-21
Status: planning detail; [Phase 71](../phase/phase-71.md) owns the real graph/video bootstrap; the applied 71–71.4 sequence owns complete implementation and acceptance
Tracking: DEV-034

## 欲しい動作

利用者は最終成果物を指定する。たとえば「日本語動画を生成して」と依頼する。
利用者に途中のDSLやハッシュ値を指定・更新させない。

```text
依頼された最終成果物
  -> 直接の入力DSL
  -> その親DSLを再帰的に確認
  -> Content Core

Content Core
  -> 古くなったDSLを依存順に更新
  -> 現在のstoryboard.md
  -> 動画を生成または更新
```

これは全成果物の一括再生成ではない。選択された成果物からCoreまでの
宣言済み依存閉包だけを処理する。Storyboardだけが変更された場合は
Coreや無関係なDSLを書き直さず、対応する動画を更新する。中間DSLが
変更された場合は、そのDSLから選択された成果物までの子孫を順に更新する。

## ノードと依存の宣言

各DSL・中間成果物・最終成果物のノードは、次を明示する。

- 一意のノードと出力パス、ロケール／プロファイル。
- 直接の親ノードと、設定・画像・音声・レンダラー入力など実際に消費するファイル。
- 内容を作成・更新する担当。意味を持つDSLはCodexによるオーサリング、
  決定的な変換・描画はCozyの既存操作など、実際に存在する経路に結び付ける。
- 入力・出力の検証、更新要否、失敗時に保持する成果物。

親子関係をファイル名、同じディレクトリ、似た文章、既存出力から推測しない。
動画リソースが`storyboard.md`を入力として指すだけでは、Coreからその
Storyboardまでの依存宣言にならない。Storyboardの親DSLと作成担当を
明示する必要がある。

今回のSimpleModeling.org `ai-development-harness` には、Document Project側の
`video/storyboard.md`とメディア側の`video/ja/storyboard.md`があり、前者は
プレースホルダーである。Coreもプロジェクト記述と一部ターゲット設定で
参照パスが異なる。Phase 71の最初の作業で正本パスと依存辺を確定し、
両経路を一つの有効な宣言に揃える。現状のパスから関係を推測して
通し動作が実装済みだと主張しない。

## 更新アルゴリズム

1. 指定された成果物から宣言済みの直接依存を逆向きにたどり、Coreと
   明示的な外部入力までのグラフを確定する。共有ノードを重複実行せず、
   循環、存在しない作成担当、必要な意味の欠落を処理前に報告する。
2. Core側からトポロジカル順に処理する。DSLが存在せず、親の更新日時が
   DSLより新しい、または単純な規則では再利用を判断できない場合は、
   宣言された作成担当でDSLを更新して検証する。意味を持つDSLをCozyが
   推測で執筆したり、単なる`touch`で更新済みと偽ったりしない。
3. 最終成果物が存在せず、直接のDSL・設定・素材・中間出力のどれかが
   最終成果物より新しい場合は再生成する。すべて有効かつ新しければ
   何も書き換えず再利用する。部分再利用を安全に判断できないときは
   選択された成果物を再生成する。
4. 失敗したノードの先へ進まない。以前の正常な成果物は保持し、今回の
   依頼で更新できたものとして表示しない。構文不正、危険なパス、
   必須入力欠落、作成担当不在、描画失敗はそれぞれ適切に報告する。

更新日時の比較、同時刻・時刻粒度・強制再生成の扱いは[Phase 60の
makeレベル方針](document-project-confirmation-views-and-make-dependencies-proposal.md)
と整合させる。DSLが意味的に変わらなくても、親が新しい場合には
作成担当が内容を確認して有効な子DSLを再出力する。無条件の時刻更新を
内容更新の代用にしない。

## ハッシュと承認の境界

2026-09-28改訂：公開・配布成果物の整合性確認という明確な目的を持つdigestを
除き、hashロジックをすべて削除する。既存の計算・保存・読込・比較や専用の
設定・モデルも対象とし、互換性・診断・将来用として残す旧方針は撤回する。
ファイル更新管理は当面、宣言済み依存関係とファイルの更新日時に基づく。
より厳密な管理が必要になった場合は、対象・依存・生成操作・生成状態を
明示した正確なメタデータ管理を設計して導入する。hashで代用しない。
詳細は[更新管理契約](../spec/file-update-management.md)を参照する。

`storyboardReview.approvedIdentity`、
視覚レビューの承認値、`confirmationReview.approvedIdentity`の欠落・不一致で
確認用動画や最終動画の生成を止めない。スキルも値を取得・転記しない。

この段階では人間の承認を動画生成の前提にしない。確認用動画は必要なときに
選ぶレビュー用成果物で、最終動画の必須の前段階ではない。将来、人間の承認が
必要になった場合は、生成物の新旧判定とは別の要求・操作として設計する。
公開・配信の承認までこの判断で省略するものではない。

## 完了判定

Phase 71の初回通し動作は、Cozy単体の動画ビルドや架空の依存グラフだけで閉じない。
実際の`ai-development-harness`の宣言を用いた隔離コピーで、同じ
「動画を生成して」という入口から次を通しで確認する。

- Core変更 → 影響する中間DSL → Storyboard → 動画の順に更新。
- 中間DSL変更 → その子孫だけ更新。Storyboard変更 → 動画だけ更新。
- 変更なし → DSLと動画の再利用。欠落・再利用判断不能 → 必要な範囲を生成。
- 上記のどれも、承認用ハッシュの編集や人間の事前承認を要求しない。

Phase 60.1はCore起点の一般的なオーサリング経路を閉じたが、当時の
通し検証は記事とHTMLの3成果物だった。動画まで動くことはPhase 71で
初めて検証する。外部のスキルやSimpleModeling.orgの宣言修正が必要なら、
実装時にその権限を別途確保する。未接続のままPhaseを完了扱いしない。

## 2026-09-29 分割後の所有境界

元のPhase番号を保持した順序は71 → 71.1 → 71.2 → 71.3 → 71.4。
71は正本パス・producer/依存・hash用途台帳と実動画までの初回通し動作、
[71.1](../phase/phase-71.1.md)は文書/media等の非整合性hash撤去、
[71.2](../phase/phase-71.2.md)は残る動画hashと表示継続・発音、
[71.3](../phase/phase-71.3.md)はsite/PDF更新・公開物整合性境界、
[71.4](../phase/phase-71.4.md)は黒い末尾の修正と全体の再検証を所有する。
上記Core起点の動作は71で実行証明し、71.4で受理済みの全変更を含むtreeで
統合確認する。全リポジトリのfull SBT testは既定のfinal-onlyで71.4に集約し、
各Phaseのfocused validation・独立レビュー・release closureは省略しない。
このノート改訂は計画の所有境界だけを変更し、実装開始や既存の完了を主張しない。
