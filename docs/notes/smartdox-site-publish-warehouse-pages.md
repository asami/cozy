# SmartDox Site Pages from publish.d

status=concept-note
published_at=2026-05-13

---

# Purpose

This note records the expected human-facing web pages generated by SmartDox site from `publish.d` metadata generated by Cozy.

In the current operation, the main paths are expected to be:

```text
publish.d  = /Users/asami/src/dev2025/simplemodeling-org/publish.d
warehouse  = /Users/asami/src/maven-repository  # indexed by Cozy, not read by SmartDox site
```

SmartDox site owns rendering and navigation. Cozy owns extraction, warehouse indexing, and metadata generation.

---

# Input Responsibilities

## publish.d

`publish.d` is the only generated data input expected by SmartDox site. It provides semantic publication metadata plus artifact/release metadata generated by Cozy from the warehouse.

Primary inputs:

- `metadata/catalog/projects/*.yaml|json`
- `metadata/catalog/samples/*.yaml|json`
- `metadata/projects/*/metadata.yaml|json`
- `metadata/samples/*/metadata.yaml|json`
- `metadata/samples/*/items/*/*/metadata.yaml|json`
- `metadata/samples/*/items/*/*/files/...`
- `metadata/artifacts/download/*.yaml|json`
- `metadata/artifacts/repository/*.yaml|json`
- `metadata/artifacts/maven/*.yaml|json`
- `metadata/source-manifest/*.yaml|json`

This layer answers:

- what project or sample exists
- where it should appear in the site
- what kind of project it is
- what source files are included
- what artifact metadata is known

## warehouse

`warehouse` provides durable binary/release artifacts, but it is consumed by Cozy through `index-warehouse`, not by SmartDox site directly.

Cozy indexes:

- Maven artifacts under `warehouse/maven`
- CAR archives under `warehouse/repository/car/<module>/<version>`
- SAR archives under `warehouse/repository/sar/<module>/<version>`
- sample collection ZIP archives under `warehouse/download/<publication.path>/<version>`
- individual sample ZIP archives under `warehouse/download/<publication.path>/<sample>/<version>`
- only repository artifact modules configured for the publication
- checksum sidecars when present

The resulting `publish.d/metadata` entries answer:

- what can be downloaded
- which versions exist
- where artifacts are stored
- what release history is available

# Core Rendering Model

The current site should be organized around two major pillars.

1. CozyTextus itself
2. Component repositories for CozyTextus

The first pillar explains CozyTextus as a product, platform, documentation system, and operating environment.

The second pillar presents component repositories as durable engineering units used by CozyTextus.

A component repository ties together:

- source repository identity
- component or subsystem artifacts
- sample and tutorial material
- source manifest
- release history
- warehouse downloads

Samples and tutorials are not isolated first-class roots in this model. They are attached to, or placed alongside, either the CozyTextus pillar or a component repository pillar as related publication views.

SmartDox site should join `publish.d` metadata entries by stable publication identity.

Example:

```yaml
publication:
  name: textus-tutorial
  title: Textus Tutorial
  path: textus/tutorial/textus-tutorial
```

This can render a human tutorial view under a non-multilingual BoK path:

```text
/textus/tutorial/textus-tutorial/
```

In a multilingual BoK such as `www.simplemodeling.org`, SmartDox site adds language prefixes:

```text
/ja/textus/tutorial/textus-tutorial/
/en/textus/tutorial/textus-tutorial/
```

However, this tutorial view should still be connected back to the component repository pillar that owns or contextualizes it.

The `name` is the stable metadata key. The `path` is the human-facing site location.

# Expected Page Types

## 1. CozyTextus Product/Platform Page

Example paths:

```text
/cozytextus/
/textus/
```

Purpose:

- explain CozyTextus itself
- present the product/platform overview
- link to manuals, tutorials, architecture, operation guides, and component repositories
- provide the conceptual entry point before entering individual component repositories

Source data:

- hand-authored SmartDox site pages
- generated `publish.d` entries when CozyTextus documentation projects are published
- `publish.d` artifact and release metadata generated from warehouse indexing when CozyTextus itself has downloadable releases

Expected content:

- CozyTextus overview
- architecture and operating model
- manuals and tutorials
- component repository catalog entry point
- release/download links when available

---

## 2. Component Repository Page

Example paths:

```text
/textus/components/<component>/
/repositories/textus-tutorial/
```

The exact URL scheme may vary, but this page is the conceptual root.

Purpose:

- present the component repository as an engineering knowledge unit
- show title, kind, organization, version, and repository role
- provide primary navigation to related samples, tutorials, source manifest, releases, and downloads

Source data:

- `metadata/catalog/projects/textus-tutorial.*`
- `metadata/projects/textus-tutorial/metadata.*`
- `metadata/samples/textus-tutorial/metadata.*` when the repository is a sample/tutorial repository
- `metadata/artifacts/maven`, `metadata/artifacts/repository`, and `metadata/releases` metadata when available
- `metadata/artifacts/download` metadata when sample ZIP downloads are available

Expected content:

- title: `Textus Tutorial`
- project kind: `sample-multi`
- current version
- repository role: component repository, sample collection, tutorial collection, or release artifact source
- links to related tutorial/sample views
- links to source manifest and release artifacts

---

## 3. Related Sample/Tutorial Collection View

Example paths:

```text
/textus/tutorial/
/textus/tutorial/textus-tutorial/
```

Purpose:

- list tutorial collections and their sample projects
- provide navigation by topic, sequence, capability, or learning path
- keep the component repository context visible

Source data:

- `metadata/catalog/samples/textus-tutorial.*`
- `metadata/samples/textus-tutorial/metadata.*`
- child sample metadata linked from the collection metadata
- `metadata/artifacts/download/textus-tutorial.*` for collection and individual sample ZIP downloads
- source manifest entries under `samples/*/build.sbt`

Expected content:

- sample list
- sample directory name
- detected title when available
- build tool metadata
- links to each sample detail page

`/textus/tutorial/` is the tutorial catalog. `textus-tutorial` is the current
collection generated from `cncf-samples`; future tutorials should be added as
sibling collections under `/textus/tutorial/<tutorial>/`.

## 5. Repository Source Manifest Page

Example paths:

```text
/textus/tutorial/textus-tutorial/source-manifest/
```

Purpose:

- show the source files included in publication extraction
- support reproducibility and AI-oriented source grounding

Source data:

- `metadata/source-manifest/textus-tutorial.*`

Expected content:

- file path table
- file size
- SHA-256 checksum
- optional grouping by directory

This page is mainly for maintainers, reviewers, and AI grounding workflows.

## 6. Repository Artifact Download Page

Example paths:

```text
/textus/downloads/
/textus/tutorial/textus-tutorial/downloads/
```

Purpose:

- expose release binaries and downloadable artifacts
- distinguish release artifacts from development-local outputs

Source data:

- `metadata/artifacts/repository/textus-tutorial.*`
- `metadata/artifacts/maven/textus-tutorial.*`
- `metadata/artifacts/download/textus-tutorial.*`
- `metadata/releases/textus-tutorial.*`

Expected content:

- latest release version
- available versions
- artifact type: Maven, CAR, SAR, ZIP, bundle
- file names
- size and checksum when available
- download links
- release notes link when available

Current limitation:

- v1 artifact metadata is generated by Cozy warehouse indexing.
- SmartDox site should not scan warehouse contents directly.

## Download URL Responsibility

`/textus/downloads` is a human-facing download catalog and guide for Textus
users.

It organizes runtime artifacts, tutorial ZIP files, sample ZIP files, CAR/SAR
artifacts, release notes, checksums, and metadata links by user intent. It does
not own artifact file bodies. Its download links point to stable artifact URLs
under `/repository/download/...`.

Tutorial-specific download pages may live under the tutorial path, for example:

```text
/textus/tutorial/textus-tutorial/downloads/
```

These pages present collection ZIP files and individual sample ZIP files in the
tutorial context. For `textus-tutorial`, this means the tutorial page explains
which ZIP to use, while the artifact body remains under the repository download
path.

`/repository/download` is the artifact body location for Cozy warehouse-derived
download artifacts.

It corresponds to `publicPath` values in
`publish.d/metadata/artifacts/download/*.json`, for example:

```text
repository/download/textus/tutorial/textus-tutorial/0.1.0-SNAPSHOT/textus-tutorial-0.1.0-SNAPSHOT.zip
repository/download/textus/tutorial/textus-tutorial/01-minimal/0.1.0-SNAPSHOT/01-minimal-0.1.0-SNAPSHOT.zip
```

This path prioritizes stable URLs, machine reference, and script access over
reader-oriented explanation.

In short:

- `/textus/downloads` is the catalog and guide.
- `/textus/tutorial/<tutorial>/downloads` is the tutorial-context guide.
- `/repository/download` is the artifact body location.
- SmartDox reads Cozy-generated `publish.d` artifact metadata to create
  human-facing pages; it does not scan the warehouse directly.

## Maven URL Responsibility

`/repository/maven` is the canonical Maven artifact body location for new
versions.

Existing artifacts already published under top-level `/maven` remain available
for backward compatibility. SmartDox should keep those old URLs intact, but new
human-facing download and catalog pages should link to `/repository/maven/...`
when Cozy `publish.d` metadata provides Maven artifact `publicPath` values.

# Human Navigation Flow

A typical reader flow:

```text
/cozytextus/
  -> component repository catalog
  -> Textus Tutorial component repository
  -> component repository page
  -> related sample/tutorial collection
  -> sample/tutorial detail page
  -> source or download page
```

A tutorial-oriented entry may start from `/textus/tutorial/textus-tutorial/`,
and additional tutorials should appear as siblings under `/textus/tutorial/`.

A maintainer flow:

```text
component repository metadata page
  -> source manifest
  -> artifact metadata
  -> publish.d release/download verification
```

# Relationship to AI-Facing Knowledge

The same pages should support AI grounding indirectly.

Human pages should expose:

- stable URLs
- normalized metadata
- source file checksums
- artifact provenance
- component repository relationships
- project/sample relationships

Future machine-facing projections may use the same inputs to generate:

- JSON-LD
- RDF
- knowledge graph edges
- search indexes
- RAG documents

The human website and machine projections should share the same `publish.d` source of truth.
