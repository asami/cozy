# Multi-Sample Project Publication Bridge

status=concept-note
published_at=2026-05-13
audience=multi-sample project contributors and AI agents

---

# Purpose

This note explains the standard publication pattern for a multi-sample project.

`cncf-samples` is the current representative example of this pattern.

The recurring failure mode is treating a sample repository as if it directly
owns website rendering or SmartDox page generation. It does not.

A multi-sample project is a source repository. Cozy extracts publication
metadata from it. SmartDox site renders that metadata into human-facing pages.

The main rule is:

```text
Do not make a multi-sample project generate the website.
Make the repository a clean knowledge source that Cozy can publish.
```

---

# Mental Model

The publication pipeline is:

```text
multi-sample project repository
  -> Cozy publish-project
  -> publish.d metadata
  -> SmartDox site rendering
  -> website.d

warehouse artifacts
  -> Cozy index-warehouse
  -> publish.d artifact/release metadata
  -> SmartDox site rendering
```

Responsibilities:

| Layer | Owns |
|---|---|
| multi-sample project | executable sample projects, source layout, sample explanations, local verification scripts |
| Cozy | extraction, normalization, source manifests, catalog metadata, artifact/release metadata |
| `publish.d` | generated semantic publication data consumed by SmartDox site |
| SmartDox site | navigation, HTML/PDF/site rendering, human-facing layout |
| warehouse | durable released binaries such as Maven artifacts, CAR, SAR, ZIP |

Important consequence:

- SmartDox site should consume `publish.d`, not scan the sample repository directly.
- SmartDox site should consume artifact metadata in `publish.d`, not scan the warehouse directly.
- The sample repository should not duplicate Cozy's metadata compiler logic.

---

# What A Multi-Sample Project Is

A multi-sample project is one repository containing multiple independent sample
projects under a common directory, usually `samples/`.

`cncf-samples` is the typical pattern instance.

Generic structure:

```text
sample-repository/
  build.sbt
  .cozy/config.yaml
  samples/
    01-minimal/
      build.sbt
      README.md
    02-component/
      build.sbt
      README.md
    ...
```

The repository is published as a sample/tutorial collection, not as a single
runtime component. Each child sample remains independently buildable, but the
publication unit is the collection.

Example publication identity for `cncf-samples`:

```yaml
publication:
  name: textus-tutorial
  title: Textus Tutorial
  path: textus/samples/tutorial
  kind: sample-multi
  samples_dir: samples
```

Meaning:

| Field | Meaning |
|---|---|
| `name` | stable metadata key and URL-safe publication identity |
| `title` | human display title |
| `path` | target path in the SmartDox site |
| `kind` | Cozy project kind; `sample-multi` means independent child sample projects under `samples/` |
| `samples_dir` | child sample directory scanned for sample project structure |

---

# Shape Rules For sample-multi

A `sample-multi` repository has two levels.

Repository level:

- owns `.cozy/config.yaml`
- owns the collection publication identity
- owns the output destination for `publish.d`
- owns shared setup scripts and repository-wide documentation

Child sample level:

- owns one independently buildable example
- usually has its own `build.sbt`
- usually has its own `README.md`
- may have run scripts, source files, and local fixtures

Do not put site publication settings into every child sample.

The child sample is content. The repository is the publication unit. Cozy is the compiler.

Current v1 metadata is collection-level plus explicit child sample records.
It records the repository source manifest and expands each child sample into a
versioned SmartDox-readable source tree.

```text
samples/01-minimal/build.sbt
samples/02-component/build.sbt
```

Per-child sample records are generated by Cozy, not by local scripts in each sample.
Each child sample record contains the expected sample ZIP path and the
`metadata/artifacts/download/<publication>` metadata reference used by SmartDox to render
download links after `index-warehouse` has run.

# What Cozy Produces For sample-multi

For a `sample-multi` project, Cozy should generate collection-level `publish.d` entries such as:

```text
publish.d/
  metadata/
    catalog/
      projects/textus-tutorial.yaml
      projects/textus-tutorial.json
      samples/textus-tutorial.yaml
      samples/textus-tutorial.json
    projects/textus-tutorial/metadata.yaml
    projects/textus-tutorial/metadata.json
    samples/
      textus-tutorial/
        metadata.yaml
        metadata.json
        items/01-minimal/0.1.0/metadata.yaml
        items/01-minimal/0.1.0/metadata.json
        items/01-minimal/0.1.0/files/...
        items/01-minimal/latest.json
    source-manifest/
      textus-tutorial.yaml
      textus-tutorial.json
```

When release artifacts exist in the warehouse, Cozy also generates:

```text
publish.d/
  metadata/
    artifacts/
      maven/textus-tutorial.yaml
      download/textus-tutorial.yaml
      download/textus-tutorial.json
      repository/textus-tutorial.yaml
      repository/textus-tutorial.json
    releases/
      textus-tutorial.yaml
    textus-tutorial.json
```

This is the data SmartDox site should render.

# Project Metadata And Local Configuration

Use `project.yaml` for public project metadata. This file is the visible place
for information such as `summary` and `description`; it is not limited to
article generation.

Example:

```yaml
project:
  name: textus-tutorial
  title: Textus Tutorial
  path: textus/samples/tutorial
  kind: sample-multi
  summary: Textus tutorial sample collection.
  description: Tutorial samples for Cozy Textus users.
```

Use `.cozy/config.yaml` for repository-local operation defaults.

```yaml
publication:
  output: /Users/asami/src/dev2025/simplemodeling-org/publish.d
  samples_dir: samples

warehouse:
  repository: /Users/asami/src/maven-repository
  maven:
    coordinates:
      - org.example:textus-tutorial_3
  repository_artifacts:
    include:
      - car
      - sar
    modules:
      - textus-tutorial
```

Guidelines:

- Put public project metadata in `project.yaml`.
- Put local output paths, warehouse settings, and operational defaults in `.cozy/config.yaml`.
- Use `build.sbt` settings only when sbt-specific override is needed.
- Do not hard-code SmartDox rendering behavior in sample build files.
- Do not make sample scripts write directly into `website.d`.

# Operations

## Generate project publication metadata

Preferred through sbt-cozy:

```console
sbt cozyPublishProject
```

Equivalent Cozy CLI:

```console
cozy publish-project . --save=/Users/asami/src/dev2025/simplemodeling-org/publish.d
```

This operation reads the multi-sample repository and produces project/source/catalog/sample metadata.

It should not publish binaries.

## Generate warehouse artifact metadata

Preferred through sbt-cozy:

```console
sbt cozyIndexWarehouse
```

Equivalent Cozy CLI:

```console
cozy index-warehouse /Users/asami/src/maven-repository \
  --save=/Users/asami/src/dev2025/simplemodeling-org/publish.d \
  --name=textus-tutorial \
  --maven-coordinates=org.example:textus-tutorial_3 \
  --repository-artifacts=car,sar \
  --repository-modules=textus-tutorial
```

This operation reads warehouse artifacts and updates artifact/release metadata
in `publish.d`.

It should not build the samples and should not render the website.

---

# Warehouse Rules

Warehouse is the fact source for distributed binaries.

Current expected layout:

```text
/Users/asami/src/maven-repository/
  maven/<group path>/<artifactId>/<version>/<files>
  repository/car/<module>/<version>/<module>-<version>.car
  repository/sar/<module>/<version>/<module>-<version>.sar
```

Rules:

- Maven indexing uses configured coordinates only.
- CAR/SAR indexing uses configured repository modules only.
- Do not scan all warehouse artifacts into one publication.
- SNAPSHOT versions may appear in metadata, but latest release should prefer a non-SNAPSHOT version.
- Cozy computes SHA-256 and reads `.sha1` / `.md5` sidecars when available.

# What Contributors Should Edit

Contributors and AI agents working in a multi-sample project should edit:

- sample `README.md` files
- sample `build.sbt` files
- sample source files
- sample run scripts
- phase/checklist documents
- `.cozy/config.yaml` when publication defaults need to change

They should not edit:

- generated `publish.d` by hand
- SmartDox site templates to compensate for missing sample metadata
- warehouse metadata files by hand
- Cozy compiler behavior from inside `cncf-samples`

If the required metadata cannot be produced from this repository, fix Cozy or
sbt-cozy instead of inventing a local workaround.

---

# How SmartDox Should See A Multi-Sample Project

SmartDox site should see the repository as one sample/tutorial collection
publication. For `cncf-samples`, that publication is currently named
`textus-tutorial`.

Expected human-facing site area:

```text
/textus/samples/tutorial/
```

Expected page roles:

| Page | Source data |
|---|---|
| Tutorial collection page | `metadata/catalog/samples/textus-tutorial.*`, `metadata/samples/textus-tutorial/metadata.*` |
| Project metadata page | `metadata/catalog/projects/textus-tutorial.*` |
| Source manifest page | `metadata/source-manifest/textus-tutorial.*` |
| Download page | `metadata/artifacts/maven/textus-tutorial.*`, `metadata/artifacts/repository/textus-tutorial.*` |
| Release history page | `metadata/releases/textus-tutorial.*` |

SmartDox may create richer navigation, but the data source remains `publish.d`.

# Common Mistakes

## Mistake: Add SmartDox page generation to cncf-samples

Wrong:

```text
cncf-samples -> website.d
```

Correct:

```text
cncf-samples -> Cozy -> publish.d -> SmartDox site -> website.d
```

## Mistake: Make sample scripts update publish.d directly

Sample scripts should demonstrate CNCF runtime behavior. They should not become
publication compilers.

Use Cozy operations for publication metadata.

## Mistake: Scan every CAR/SAR in the warehouse

A shared warehouse contains unrelated artifacts. Index only configured modules.

Correct:

```yaml
warehouse:
  repository_artifacts:
    modules:
      - textus-tutorial
```

## Mistake: Treat `name` as display text

`name` is a stable slug. Use `title` for display text.

Correct:

```yaml
publication:
  name: textus-tutorial
  title: Textus Tutorial
```

## Mistake: Put generated output policy into every sample

Publication output is repository-level configuration. Child samples should stay independent and focused on execution.

# Minimal Task Checklist For AI Agents

Before changing `cncf-samples`, decide which category the task belongs to.

## Sample behavior task

Do:

- update the relevant sample directory
- keep the sample independently buildable/runnable
- update its README/checklist
- run the sample-specific validation

Do not:

- touch Cozy publication compiler logic
- change SmartDox site rendering

## Publication metadata task

Do:

- update `.cozy/config.yaml` when defaults are wrong
- run `sbt cozyPublishProject`
- inspect generated `publish.d` metadata shape
- update notes/specs if the model changed

Do not:

- hand-edit `publish.d`
- add per-sample hacks to generate publication metadata

## Artifact/release metadata task

Do:

- ensure artifacts are in warehouse
- configure Maven coordinates and repository modules
- run `sbt cozyIndexWarehouse`
- inspect `metadata/artifacts/maven`, `metadata/artifacts/repository`, and `metadata/releases` under `publish.d`

Do not:

- make SmartDox scan warehouse directly
- index unrelated repository modules

# Current Boundary Statement

A multi-sample project owns executable examples.

Cozy owns the publication compiler.

SmartDox owns rendering.

Warehouse owns durable release artifacts.

When in doubt, preserve this boundary instead of making a local workaround in the sample repository.

# Concrete Example: cncf-samples

`cncf-samples` is the reference `sample-multi` repository for this pattern.

Repository path:

```text
/Users/asami/src/dev2026/cncf-samples
```

Publication target:

```text
/Users/asami/src/dev2025/simplemodeling-org/publish.d
```

Warehouse target:

```text
/Users/asami/src/maven-repository
```

Human-facing SmartDox path:

```text
/textus/samples/tutorial/
```

Publication identity:

```yaml
publication:
  name: textus-tutorial
  title: Textus Tutorial
  path: textus/samples/tutorial
  kind: sample-multi
  output: /Users/asami/src/dev2025/simplemodeling-org/publish.d
  samples_dir: samples
```

Why `name` is `textus-tutorial`:

- it is the stable publication key used in `publish.d`
- it is URL-safe
- it is not necessarily the same as the repository directory name
- it represents the tutorial/sample collection as presented to readers

Why `kind` is `sample-multi`:

- the repository contains many independent sample projects
- child samples live under `samples/`
- each child sample can have its own `build.sbt`, README, and scripts
- the publication unit is the collection, not one child sample

# cncf-samples Project Metadata And Config

Recommended public metadata:

```yaml
# cncf-samples project.yaml
project:
  name: textus-tutorial
  title: Textus Tutorial
  path: textus/samples/tutorial
  kind: sample-multi
  summary: Cozy Textus tutorial sample collection.
  description: Executable sample projects that demonstrate Textus and CNCF usage patterns.
```

Recommended local operation settings:

```yaml
# cncf-samples .cozy/config.yaml
publication:
  output: /Users/asami/src/dev2025/simplemodeling-org/publish.d
  samples_dir: samples
  source_manifest:
    excludes:
      - target
      - .git
      - .bsp
      - .metals
      - .idea
      - repository.d

warehouse:
  repository: /Users/asami/src/maven-repository
  maven:
    coordinates:
      - org.example:textus-tutorial_3
  repository_artifacts:
    include:
      - car
      - sar
    modules:
      - textus-tutorial
```

Notes:

- `publication.output` points to the SmartDox publication workspace, not to `website.d`.
- `warehouse.repository` points to the durable binary store.
- `warehouse.repository_artifacts.modules` prevents unrelated CAR/SAR files from being indexed.
- The Maven coordinate shown above is illustrative; use the real coordinate when the project publishes a Maven artifact.

# cncf-samples Expected publish.d Meaning

## `metadata/catalog/projects/textus-tutorial.*`

Represents the repository-level project entry.

SmartDox can use it for:

- component/sample repository catalog
- project metadata page
- repository role explanation

## `metadata/catalog/samples/textus-tutorial.*`

Represents the sample/tutorial collection entry.

SmartDox can use it for:

- tutorial index page
- sample collection listing
- navigation into child sample pages
- direct traversal to `metadata/samples/textus-tutorial/metadata`
- direct traversal to `metadata/artifacts/download/textus-tutorial` when downloads exist

## `metadata/samples/textus-tutorial/metadata.*`

Represents collection-level sample metadata.

SmartDox can use it for:

- display title
- site path
- collection kind
- child sample item metadata links
- links to source manifest and downloads

## `metadata/source-manifest/textus-tutorial.*`

Represents the files included in the publication source snapshot.

SmartDox and AI-facing tools can use it for:

- reproducibility
- source grounding
- child sample inference
- checksum-based change detection

## `metadata/artifacts/maven`, `metadata/artifacts/repository`, `metadata/artifacts/download`, and `metadata/releases`

Represent publish.d metadata for Maven, expected repository/download paths, and release history. Maven metadata is indexed from the warehouse; repository/download metadata is written by `publish-project` and checked by `index-warehouse`.

Sample ZIP archives are user-facing downloads. `publish-project` writes their expected paths in `publish.d`; `cozyDistributeSamples` places both the collection archive and individual sample archives at:

```text
warehouse/download/samples/<publication>/<version>/<publication>-<version>.zip
warehouse/download/samples/<publication>/<sample>/<version>/<sample>-<version>.zip
```

The collection archive contains all child sample directories. Individual sample archives contain one child sample project.

CAR/SAR archives are runtime repository artifacts. `publish-project` writes their expected paths in `publish.d`; `cozyDistributeCAR/SAR` places the files at:

```text
warehouse/repository/car/<module>/<version>/<module>-<version>.car
warehouse/repository/sar/<module>/<version>/<module>-<version>.sar
```

SmartDox can use them for:

- download pages
- release history pages
- artifact provenance
- checksum display

# cncf-samples Agent Rules Of Thumb

When asked to work on `cncf-samples`, first classify the task.

If the task is about a sample's behavior:

```text
Edit samples/<name>/...
Run that sample's checks.
Update that sample's README or phase checklist.
```

If the task is about publication:

```text
Check .cozy/config.yaml.
Run cozyPublishProject.
Inspect publish.d metadata.
Do not hand-edit publish.d.
```

If the task is about releases or downloads:

```text
Check warehouse contents.
Run cozyIndexWarehouse.
Inspect maven/repository/releases metadata.
Do not make SmartDox scan the warehouse.
```

If the task is about page design or rendering:

```text
Work in SmartDox site, not cncf-samples.
cncf-samples provides data, not page templates.
```

If the task needs metadata Cozy cannot currently produce:

```text
Fix Cozy or sbt-cozy.
Do not add ad hoc metadata generation scripts to cncf-samples.
```

# cncf-samples Anti-Patterns

Avoid these changes:

- adding `website.d` generation scripts to `cncf-samples`
- putting SmartDox page templates in child sample directories
- making every child sample write its own `publish.d` files
- scanning all `/Users/asami/src/maven-repository` artifacts for `textus-tutorial`
- using repository directory name as the publication identity when the published collection name is different
- treating `samples/01-minimal` as a separate top-level publication unless that is explicitly designed

Preferred shape:

```text
cncf-samples
  -> one sample-multi publication: textus-tutorial
  -> many child sample projects under samples/
  -> Cozy-generated publish.d
  -> SmartDox-rendered pages
```
