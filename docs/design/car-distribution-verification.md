# CAR配布検証とコンポーネント・リポジトリの責務

Status: adopted future design; implementation is planned in Phase 82.
Decision date: 2026-10-09.
Behavior authority: [配布・取得仕様](../spec/car-distribution-verification.md).

## 境界

配布検証の境界を、ローカルキャッシュへのダウンロードと受け入れに置く。
完成したCARの全バイトを対象に、外部SHAで取得物の破損を検出し、
電子署名がある場合は信頼する提供者の署名を検証する。
受け入れたそのCARを保存してから、展開・ローディングへ渡す。

署名は任意とする。未署名CARもSHA照合後に受け入れる。
署名付きCARの検証失敗を、未署名の受け入れへ切り替えない。
署名の存在判定は、正常な未署名状態と取得障害を区別できる配布契約にする。

## 責務分担

| 境界 | 責務 |
| --- | --- |
| Cozyの通常の開発用CAR生成 | モデル・宣言・実行資源からCARを生成する。公開用SHA・署名を必須にしない。 |
| Cozyの公開用配布物準備 | 完成したCARに対応するSHAと任意の署名を生成する。 |
| コンポーネント・リポジトリ | CARと付属物を配布し、namespaceと許可された提供者の鍵情報を公開する。 |
| CNCFの取得・キャッシュ登録 | SHAと任意の署名を検証し、成功した取得物だけを使用可能にする。 |
| CNCFのCARローディング | 識別情報・runtime範囲・実行に必要な形式を確認する。取得時の全体検証を繰り返さない。 |
| カタログ・利用者ツール | ABIメタデータを利用し、その用途に必要な形式を確認する。 |

Cozyは公開用の署名生成を担当し、CNCFは秘密鍵を持たずに検証する。
リポジトリ運用は、公開鍵の登録・権限付与・更新・失効と信頼鍵の案内を担当する。
取得・キャッシュ・ローディングは
[CNCF Phase 104](../../../cloud-native-component-framework/docs/phase/phase-104.md)のconsumer計画で扱う。
両側の計画文書の作成を、CNCFや公開サイトの実装・配備完了とは扱わない。

## 信頼の起点

```text
利用者が登録したリポジトリの信頼鍵
  → 署名付きのnamespace・提供者鍵情報を検証
    → 対象namespaceに許可された鍵を選択
      → 完成したCAR全体の署名を検証
```

CAR、署名、公開鍵を同じ取得元から得ただけでは、提供者の真正性を保証できない。
リポジトリの信頼鍵を最初にどう登録するかを運用契約に含める。
公開鍵を配布する機能を、無条件に公開鍵を信用する機能にしない。
提供者の鍵更新とリポジトリの信頼鍵更新は別の手順として定義する。

## キャッシュの責務

取得中のCARは使用可能なキャッシュと分ける。取得・検証成功をキャッシュ登録の条件にする。
登録後は取得処理が所有し、通常の開発用出力や利用者による編集の対象にしない。
再取得・更新では再び取得時の検証を行う。

再利用時の全ファイルハッシュ台帳、毎回の読み直し、classローダーへの独自検証を設けない。
取得時の検証を省略するための保存管理と、編集可能な保存物の再検証を混同しない。
通常のI/O失敗処理は必要だが、この境界をCozy全体の生成物管理へ拡張しない。

## ABIメタデータ

ABI manifestの価値は、コンポーネントの公開契約を利用者やツールへ伝えることにある。
CAR受け入れ時に宣言の一部だけを検査しても、classとの一致やバイナリ互換性は保証しない。
メタデータは維持し、生成・公開・利用の各処理が必要な検証を担当する。
前リリースとの公開契約比較を行う`cozy lint abi`は独立した責務として維持する。

## 現行の除去方針との関係

[Artifact Protection Removal](artifact-protection-removal.md)はPhase 71.5の
開発・生成・既存公開経路における除去方針である。
本設計は2026-10-09の追加指示による、将来の公開リポジトリ取得境界だけを対象にした新機能である。
Phase 71.5の未完了義務を移したり、除去対象を温存する例外にはしない。
現行の公開設計がSHA sidecarを出さない記述は、現在の契約として保持する。
Phase 82の実装時に、該当する既存spec/designとExecutable Specificationを明示的に更新する。

署名形式や鍵情報のwire形式は、[検討メモ](../notes/car-distribution-verification.md)の
未確定事項から選定する。本設計は具体的な暗号方式や独自鍵配布プロトコルの採用を先取りしない。
