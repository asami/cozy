# Document Project: External WorkRoot and editable package design

Status: Phase 90 design; implementation pending. Contract: [specification](../spec/document-project-external-workroot.md). Planning origin: [proposal](../notes/document-project-private-package.md).

## Problem and boundary

An editable project and its selected deliverables can live in a synchronized package. Generation must execute outside that package and the project, including transient child-process writes. ProjectRoot is the admitted editable project; PackageRoot is the destination containing `source/` and selected products; WorkRoot is a local execution root outside both and outside the synchronization area. WorkRoot contains disposable `target/` work. Placement and generation are distinct operations; the source at the destination becomes the editable authority after initial placement.

The design retains the native producer graph and the existing public export boundary. It does not grant cloud publication, upload, source deletion, or synchronization conflict merging. External WorkRoot is an explicit opt-in contract for the Phase 90 routes; existing ordinary routes retain their current contract until migrated.

## Resource and ownership model

Authored Core, localized Documents, the unified `index.dox`, source SVG, slide IR, video storyboard/scripts, persistent media and style settings, and necessary images are editable inputs. Their role, not extension, controls treatment. Selected PDF, PNG, slide PDF, audio and video are deliverables; review HTML and confirmation images are work products unless explicitly selected. Intermediate audio, part video, copied inputs, logs, bundles, caches, LaTeX files, temporary state and receipts are work artifacts. Never delete or reclassify handwritten settings or existing products as disposable based on extension or location.

A package declaration owns an explicit set of destination relative output paths, keyed by product and locale. It cannot claim existing unrelated files. Existing project, existing package files, tracked files and `.gitignore` remain intact. The initial placement copies the admitted source closure; it records unresolved absolute references rather than silently rewriting strings. A user-specified mapping resolves an absolute asset to a copied package-relative resource, and links to other documents are either packaged with their closure or remain explicit external dependencies. Missing resources stop placement. Project-relative paths are preserved or deliberately rewritten with parsed reference semantics. Build-only inputs are materialized into a run directory with references resolved there; source remains unchanged.

## Execution and recovery

Each invocation owns a unique WorkRoot `target/document-project/runs/<run-id>/` subtree. All temp directories, copied inputs, provider output, logs and diagnostic state belong there. Successful candidates remain there until explicit refresh. Failed/interrupted runs retain diagnostics and candidates for inspection; explicit cleanup may remove only their owned subtree. No fallback into project, package or synchronized location is allowed. Before any effects, admission checks WorkRoot availability and compares its physical path with ProjectRoot, PackageRoot and every explicitly identified synchronization root. Equality and ancestor/descendant overlap in either direction are rejected. Resolve existing path components through symlinks to their real paths and append normalized prospective components to the nearest existing real ancestor; reject paths whose physical identity cannot be resolved unambiguously. For example, a synchronization root under `WorkRoot/target/document-project` would contain run artifacts even though WorkRoot itself is outside that root, so this arrangement is rejected. This boundary applies throughout normal, failed and interrupted runs.

Before any destination write, placement or refresh preflights all selected output file paths using the same physical-path resolution. It rejects identical aliases, ancestor/descendant pairs and any existing parent whose shape conflicts with the required directory path. For example, `report` and `report/page.pdf` cannot both be output files. Destination ownership is also checked before a writer starts; a failed preflight leaves every destination untouched.

A successful generation never modifies package products. Refresh copies only successful selected candidates to declared owned names. A cross-filesystem copy cannot be atomically replaced without a temporary file in the destination, which this contract disallows. Before each direct replacement, retain the prior bytes and an ordered per-file progress record under WorkRoot; on failure or interruption report completed, uncertain and untouched paths. Retry restores uncertain files from backup or completes them from candidate after checking destination ownership; restoration failure remains explicit. Multi-file refresh is not atomic and concurrent external edits require user reconciliation. The implementation must not claim success until every requested path is verified. It must never remove unrelated files.

P90-02 owns propagation, provider and child API adaptation and running-write observation. P90-03 owns placement, refresh and recovery. P90-04 owns isolated JA/EN acceptance, original-product preservation and final verification. These are pending; this design does not assert they already work.
